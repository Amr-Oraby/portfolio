# Skeleton Typing Animation — Hero Feature Planning

We want to replace the current static skeleton image in the Hero section with a smooth, infinitely looping typing animation using the video we created of our skeleton typing on a laptop.

The video is approximately **3 seconds long**. We want to extract it into image frames with transparent backgrounds and use those frames to create an animation inside the existing Hero component.

We already have a skill named **`skeleton-animation-skill`** that contains the workflow and technical standards for our skeleton animations. Read it thoroughly and follow it as the primary reference.

**This task is planning and investigation ONLY. Do not implement anything yet.**

---

## 1. Feature Goal

Replace the current static skeleton image in the Hero section with an animated version of the same skeleton typing on its laptop.

The final animation should:

- Look like the skeleton is actively typing on the keyboard.
- Have continuous, natural finger and hand movement.
- Loop infinitely without a noticeable visual jump.
- Preserve the exact appearance and identity of our existing skeleton.
- Work perfectly with the existing Hero layout.
- Be responsive across desktop, tablet, and mobile.
- Support both light mode and dark mode.
- Be optimized for performance and minimal impact on initial page loading.

The animation should feel alive, subtle, and polished—not like a slideshow of disconnected images.

## 5. Frame Extraction — Critical Requirements

Use the established workflow from `skeleton-animation-skill` and FFmpeg where appropriate.

Extract the video into sequential image frames.

The extraction must be precise and visually clean.

### Every frame must:

- Contain ONLY the skeleton, laptop, and elements that belong to the character.
- Have a genuinely transparent background.
- Preserve the skeleton's original black outlines.
- Preserve the keyboard, laptop, hands, and fingers.
- Avoid damaging thin bone details.
- Have consistent dimensions.
- Maintain consistent character scale.
- Preserve alignment between frames.
- Avoid unwanted movement or jitter caused by inconsistent cropping.
- Avoid white halos or background remnants.
- Avoid ghosting or leftover pixels from the original background.
- Avoid clipping any part of the skeleton or laptop.

### Background removal is especially important.

Do not simply convert the background to black, white, or another color.

The final images must support transparency and work on both light and dark backgrounds.

Investigate the most reliable way to remove the video background without destroying:

- Thin black outlines.
- Finger details.
- Small gaps between bones.
- Laptop edges.
- Keyboard details.
- Any anti-aliased pixels around the skeleton.

If the source background makes clean extraction difficult, identify the appropriate solution before implementation rather than accepting low-quality frames.

Visually inspect representative frames, including frames where hands overlap the laptop or the skeleton's outlines are difficult to separate from the background.

## 6. Frame Count & Smoothness

Do not arbitrarily choose a small number of frames.

Analyze the original video and the skill's recommended approach to determine the optimal extraction rate.

The goal is to preserve the natural typing movement, especially the movement of:

- Fingers.
- Hands.
- Wrists.
- Arms.
- Upper body, if animated.

Avoid:

- Noticeable jumps between frames.
- Duplicate frames that do not add smoothness.
- Excessive frame count that unnecessarily increases asset size.
- Interpolation that introduces distorted hands or bones.

If frame interpolation is needed, investigate its quality and whether it is actually beneficial for this particular video.

Determine the best balance between:

- Smooth animation.
- Image quality.
- Frame count.
- Total asset size.
- Browser performance.

## 9. Animation Implementation

Use **GSAP** for the animation if it is consistent with the existing architecture and the skill.

Investigate the most efficient way to display the sequential frames.

The implementation should:

- Render the correct frame sequence.
- Play continuously.
- Loop infinitely.
- Maintain a consistent frame rate.
- Avoid noticeable flickering.
- Avoid unnecessary React rerenders on every frame.
- Avoid creating excessive DOM elements.
- Avoid restarting the animation due to unrelated component updates.
- Properly clean up animation instances.
- Avoid conflicts with other Hero animations.
- Work correctly with React lifecycle and Strict Mode, if enabled.

### Typing behavior

The skeleton should look like it is continuously typing.

Evaluate the best loop strategy:

- Loop the extracted sequence seamlessly.
- If the first and last frames do not match, determine how to create a natural loop.
- If necessary, use a carefully designed transition or loop sequence that avoids a visible reset.
- Do not create an awkward pause at the end of each loop.
- Avoid a robotic or repetitive visual reset.

The animation must continue indefinitely while the Hero is visible.

- The laptop remains readable.
- No white rectangular background appears around the frames.
- No background-removal artifacts become more visible when switching themes.

## 12. Performance & Loading Optimization

Performance is a high priority because the animation appears inside the initial Hero section.

Investigate:

- Total frame count.
- Total asset size.
- Individual frame sizes.
- Image decoding cost.
- Memory usage.
- Browser caching.
- Preloading strategy.
- Whether all frames should be loaded immediately.
- Whether frames should be loaded progressively.
- Whether the animation should start only after enough frames are ready.
- Whether the animation could affect LCP or initial rendering.
- Mobile memory and CPU usage.
- Low-end device performance.

Avoid loading hundreds of large images unnecessarily.

Determine whether the best approach is:

- Preloading all frames.
- Preloading a small initial batch and loading the rest progressively.
- Buffering frames ahead of playback.
- Using a different rendering strategy if it provides significantly better performance.

The skeleton should not delay the rest of the Hero content or website from rendering.

Avoid unnecessary libraries and dependencies.
